
# 03AD — Exact Candidate B OpenDataLoader Workbench Comparison Boundary

## Purpose

State exactly what Candidate B v1 is allowed to do.

---

## A. Exact boundary statement

Candidate B v1 is a **tests/report-only, side-by-side comparator** that:
- consumes the existing manifest-driven lower-layer NRC APS corpus,
- runs OpenDataLoader locally through the Python wrapper,
- derives semantic/layout comparison summaries,
- compares those summaries against the live lower-layer outputs and live lower-layer invariants,
- emits workbench reports under `tests/reports/...`,
- and changes nothing about runtime connector behavior.

---

## B. Exact inputs

Candidate B v1 consumes:
- the existing corpus manifest and current fixture PDFs
- the current lower-layer outputs generated by `nrc_aps_document_processing.process_document(...)`
- the current lower-layer invariants encoded in `tests/test_nrc_aps_document_processing.py`

---

## C. Exact outputs

Candidate B v1 may emit only:
- raw OpenDataLoader JSON/Markdown/image outputs under a run-scoped tests-side raw-output root
- a Candidate B proof report
- a Candidate B compare report
- optional labels/manifest sidecars under the corpus fixture folder

---

## D. Explicit non-goals

Candidate B v1 does not:
- become a connector mode
- become a new selector
- become a new runtime parser path
- replace the PyMuPDF lower layer
- change OCR/media routing
- change `visual_page_refs` semantics
- alter artifact ingestion
- alter review/runtime surfaces
- alter endpoints or run-detail refs

---

## E. Limitation controls that must remain explicit

Candidate B v1 must explicitly carry these limitation/control classes:
- vector-heavy pages
- scanned OCR-dependent pages
- visual-preservation pages already governed by the current owner path
- cases where OpenDataLoader’s semantic richness is not program-relevant

If Candidate B claims wins on those classes without a separate proof and explicit scope change,
that is a planning violation.
