4. Design Intent Summary

Layer 3 is intended to be a user-facing analytical workbench/controller that lets an operator express an investigative or analytical objective, gather and approve relevant materials, transform those materials into typed analysis-ready units, configure how analysis should be orchestrated, run analysis across one or more analysis planes, and inspect generated insights/facts/data with provenance back to the original ingress objects.

The intended user experience is not just a static report viewer. It is a stateful operator workflow with multiple review/approval boundaries.

The core user-facing loop is:

1. User states what they want to investigate.
2. User optionally gives manual/custom source and topic constraints.
3. System retrieves or locates relevant data/content/files.
4. User reviews and accepts/rejects/isolates retrieved material.
5. Accepted material is stored/frozen as session material.
6. System types and groups the material into analysis units, groups, and sets.
7. User reviews or configures the planned analysis.
8. Analysis planes execute.
9. Outputs are validated, frozen, and displayed as insights/facts/data tied to ingress objects.
10. Outputs can be packaged, reviewed, and handed off downstream.

5A. Frontend / UI Layout And Presentation Intent

Status:

- This section captures what the mockups visually communicate about how the Layer 3 frontend should look and feel in use.
- It is mockup-observed design intent, not a live implementation claim.
- By itself this broader spec does not require pixel-perfect reproduction of every diagram; the later dedicated mockup-theme freeze does require pixel-perfect treatment for the selected first-slice frames and must govern that theme-specific work.
- It does not choose a final frontend framework, component library, responsive breakpoint system, CSS implementation, or browser route.
- It should be used to guide future UI planning so the mockups are not reduced to only backend workflow/state-machine semantics.

Overall presentation model:

- Layer 3 is visualized as an operator workbench, not as a marketing/landing page and not as a passive report viewer.
- The UI is shown in a browser-like shell with a dark workspace background, a large central work area, and high-contrast panels.
- The main experience is a workflow surface: the user sees where they are in the process, what material is moving forward, what review/approval boundary comes next, and which analysis plane will receive which material.
- The mockups favor a spatial, diagrammatic layout where major Layer 3 stages are visible together, connected by arrows and grouped inside sublayer boundaries.
- The UI should communicate state and data flow visually, but the final implementation may translate the canvas into a scrollable, tabbed, stepped, split-pane, or dashboard-like interface if that is more usable.

Observed high-level layout:

- A top-level "Layer 3" context frames the whole workflow.
- The core flow reads mostly left-to-right:
  - Pre-3A intent/source setup.
  - Sublayer 3A / Gate B material intake and session scoping.
  - Sublayer 3B / Gate C typing and unit/group/set formation.
  - Sublayer 3C analysis execution environments.
  - Generated insights/facts/data and downstream output/package concepts.
- Vertical grouping is also important:
  - User input panels are stacked vertically.
  - Gate B ingress objects are grouped in a ledger-like grid.
  - Gate C typed material is grouped by quantitative, qualitative, and hybrid/mixed categories.
  - Analysis planes are stacked as separate execution environments.
- Dashed outer boundaries visually distinguish sublayers, gates, and execution regions from ordinary object cards.
- Arrows represent progression, routing, and dependency. They should not be treated as decorative only.

Initial intent-entry screen:

- The first visible user-facing screen is a centered panel inside a dark browser/workbench shell.
- It contains two large input sections:
  - "User Natural Language Query Input".
  - "User Manual/Custom Specification".
- The sections are separated by an "OR" label in the mockup.
- The action text explicitly leaves open whether the user may use natural-language input, manual/custom input, or both together.
- Therefore, the final UI must not hard-code mutual exclusivity unless a later product decision chooses it.
- The natural-language area should present a large prompt/query field with example text and enough space for contextual intent.
- The manual/custom area should present selectable or editable source/topic/focus chips rather than a plain text-only field, because the mockup shows many small keyword/source tiles.
- The confirm/submit action sits below the two entry modes and visually commits the user's selected intent/source posture.

Specific scenario presentation:

- The scenario mockup shows a concrete query about federal infrastructure spending, semiconductor production facilities, domestic auto manufacturing investments, import dependency, and labor-market shifts.
- The scenario mockup also shows many manually chosen source/topic tiles.
- This implies the UI should support a dense but readable multi-source selection layout.
- Source/topic selections should be visibly inspectable before submission.
- The UI should distinguish example/placeholder content from user-entered or selected session content.
- The source-selection area should be able to represent government agencies, industry associations, companies, report families, trade/labor data, policy concepts, and project/run artifacts in one surface.

Pre-3A / source-plane presentation:

- Pre-3A is shown as an early zone before committed Layer 3 material intake.
- Upstream feeders and/or DBs are shown as separate source boxes feeding toward Sublayer 3A.
- A future UI should make source origin visible before material is admitted into the session.
- Source origin can be presented as source cards, connector rows, filters, or grouped sections, but the operator should be able to tell whether material came from:
  - upstream feeders/storages/DBs,
  - local directories or uploaded files,
  - chooseable connectors/options,
  - existing project run artifacts,
  - or manually selected source/topic constraints.
- The mockup does not define exact source-picker controls, authentication handling, local file browser behavior, upload retention, or connector configuration.

Sublayer 3A / Gate B presentation:

- Sublayer 3A is shown as a bounded region labeled "Material Intake & Session Scoping".
- Gate B is shown as "Session Entry / Material Ledger".
- Ingress objects are shown as repeated compact chips/cards in a grid-like material ledger.
- The repeated "Gate B Ingress Object #n" visual pattern implies the operator should be able to review many candidate materials at once.
- The UI should support scan-friendly material review with enough metadata to decide approve, deny, remove, isolate, or keep for later review.
- Color outlines appear to group ingress objects. The diagrams suggest grouping by later type/category/route, but the exact color semantics are not frozen.
- The material ledger should not be a purely visual list; it must connect to durable session/material identity if implemented.
- The mockup does not define whether Gate B object cards are table rows, cards, chips, graph nodes, or a mixed presentation.

Post-3A / Pre-3B presentation:

- The mockup labels a transition where approved material is saved/frozen into a temp/local/dedicated Layer 3 DB/storage before Gate C.
- The UI should make this transition visible as a state change rather than silently moving items forward.
- The operator should be able to distinguish candidate material from approved/frozen session material.
- Future UI should show validation status for material before Gate C receives it.
- Exact status labels, progress indicators, failure states, and retry/reopen behavior remain unresolved.

Sublayer 3B / Gate C presentation:

- Sublayer 3B is shown as a bounded typing and formation region.
- Gate C is shown as "Typing + Set Formation".
- Typed material appears in separate grouped panels:
  - Quantitative Data.
  - Qualitative Data.
  - Hybrid/Mixed Data.
- The grouping implies that the UI should show both source material and its typed analysis-readiness classification.
- Gate C should help the operator understand how ingress objects became analysis units, groups, and sets.
- The UI should expose ambiguous or unsupported typing instead of silently placing material into a plane.
- The mockup does not define the exact unit/group/set visualization. It could be grouped cards, tables, nested chips, graph lanes, or a dedicated relationship view.

Sublayer 3C / analysis-plane presentation:

- Sublayer 3C is shown as a large analysis execution region containing separate analysis environment/container/plane panels.
- At minimum, the mockup shows:
  - Quantitative and/or deterministic analysis plane.
  - Qualitative data analysis plane.
  - Hybrid/mixed plane in the broader overview.
- Each analysis plane is visually structured as:
  - an input/object list on the left,
  - a middle execution/process note or orchestration block,
  - an output grid/list on the right.
- This suggests a future UI should preserve the operator's ability to see which typed objects feed which analysis process and which outputs are produced from that process.
- The diagrams do not fully specify the controls inside the orchestration block.
- The final UI must not imply that qualitative or hybrid execution is live unless a later implementation lane activates it.

Output presentation:

- Outputs are shown as repeated cards labeled "Insights/Facts/Data Generated (specific to Ingress Object #n)".
- This implies output cards should retain traceability back to the ingress objects and analysis plane that produced them.
- The UI should not present outputs as free-floating narrative with no provenance.
- Output presentation should distinguish at least:
  - generated insight/fact/data cards,
  - validation/verification state,
  - caveats or unsupported claims,
  - package/handoff readiness where applicable.
- The mockup does not define the final taxonomy of insight, fact, datum, finding, caveat, contradiction, warning, or output package.

Progressive disclosure and navigation:

- The mockups show multiple workflow stages simultaneously, which is useful for explanation.
- Later slides preserve a condensed version of the original intent-entry panel above the active flow, suggesting that session intent and selected source posture should remain visible or recoverable while the operator works downstream.
- A production UI may need progressive disclosure to avoid an oversized canvas becoming difficult to operate.
- Acceptable implementation patterns could include:
  - a full-workflow overview with clickable stage regions,
  - a stepper/state-machine navigation around draft_selection through package_review,
  - split panes where current-stage details appear alongside a compact workflow map,
  - a persistent session-context header or collapsible intent/source summary,
  - tabs for Gate B ledger, Gate C typing, plan review, execution, results, and package review.
- Any such implementation should preserve the mockup's core intent: the operator can see how user intent becomes material, how material becomes typed analysis units, how units feed analysis planes, and how outputs trace back.

Explanatory panels and annotations:

- Later userflow screenshots show large side panels containing Action/Event explanatory text.
- Those panels are valuable evidence for workflow semantics and userflow explanation.
- They should not automatically be treated as required production UI panels.
- A future production UI may translate this explanatory content into:
  - contextual help,
  - onboarding/tooltips,
  - state descriptions,
  - audit/progress summaries,
  - or non-production documentation outside the app.
- If these panels become part of the live UI, the implementation should distinguish explanatory copy from operator controls and durable session data.
- The label "(Triggered by user interaction)" should remain descriptive context for action arrows unless a later design decision turns it into a visible event/state label.

What appears semantic versus illustrative:

- Semantic or likely-semantic visual elements:
  - stage ordering from input to retrieval/intake to typing to analysis to output,
  - sublayer/gate boundaries,
  - ingress-object repetition,
  - grouping by quantitative/qualitative/hybrid categories,
  - arrows showing material and output flow,
  - separate analysis plane containers,
  - output cards tied to ingress objects,

Presentation constraints for future implementation planning:

6. Core Terminology

Layer 3:

- The overall user-facing analysis/workbench layer.
- Includes frontend/UI, session orchestration, material intake, typing, analysis execution, output generation, and backend persistence/handoff.

Pre-3A:

- The state before material is committed into Layer 3 session intake.
- In the mockup this includes user intent entry, manual/custom specification, and initial source discovery.

Gate A(?):

- Shown in the mockup as uncertain.
- Appears to represent an early pre-intake boundary before Gate B.
- Not yet clearly defined enough to treat as a durable architecture term.

Source-plane Material Intake:

- Exact visible mockup label: "( Source-plane Material Intake )".
- Appears to name the early source-discovery and material-intake zone before or around Sublayer 3A / Gate B.
- Should not be treated as a separate implemented service or durable route until a later planning pass defines whether it is a UI section name, architectural layer, or descriptive label.

Sublayer 3A:

- Material Intake & Session Scoping.
- Mockup labels this as the area where retrieved/located data/content/files enter Layer 3 for review and session scoping.

Gate B:

- Session Entry / Material Ledger.
- The operator-facing and backend-facing boundary where retrieved material becomes session-scoped material.
- The mockup repeatedly labels items as "Gate B Ingress Object #n".

Ingress Object:

- A material item entering the session through Gate B.
- Could be a file, dataset, document, connector result, local upload, run artifact, collection, or other retrieved object.

Post-3A / Pre-3B:

- Frozen/saved state after Gate B approval and before Gate C typing.
- Mockup describes this as temp/local/dedicated Layer 3 DB/storage.

Session-scoped Materials / Material Snapshots:

- Exact visible mockup label: "Session-scoped Materials / Material Snapshots".
- Represents material that has been admitted into the Layer 3 session boundary and frozen/saved enough to be referenced downstream.
- Repo-live backend maps most closely to L3MaterialSnapshot, but the mockup label should remain broader until retention, storage, and snapshot semantics are finalized.

Sublayer 3B:

- Typing, Unit/Group/Set Formation.
- The point where material is classified and prepared for analysis.

Gate C:

- Typing + Set Formation boundary.
- Converts accepted material snapshots into analysis records, units, groups, and sets.

Sublayer 3C:

- Analysis Execution Environments.
- Includes quantitative/deterministic, qualitative, and hybrid/mixed analysis environments/containers/planes.

Analysis Plane:

- A type-specific execution environment.
- Mockup includes:
  - Quantitative and/or deterministic plane.
  - Qualitative data analysis plane.
  - Hybrid/mixed data plane.

Insights/Facts/Data Generated:

- Output objects produced after analysis is executed, validated/verified, finalized, saved/frozen, and handed off.
- Mockup shows outputs as specific to Ingress Object #n.

Workbench/Controller:

- The broader repo-planned operator surface that would own the end-to-end Layer 3 lifecycle beyond the currently live bounded explicitly frozen slices.
- Current main already ships the bounded /review/layer3 and /api/v1/layer3/... workbench family from PR #184 onward.
- Current main also includes later explicitly frozen bounded slices for plan preview, plan approval/revision, execution readiness/selection/start, result status/review, package review/construction/submit, handoff/export preparation, APS handoff dispatch, external export/download readiness and same-origin delivery, plus subsequent Workbench visual/state-continuity passes. These additions still do not activate the full mockup workflow, qualitative/hybrid execution, public/signed URLs, connector dispatch, generic downstream dispatch, package mutation/reconstruction, source/schema/runtime widening, or full mockup behavior.
- Those same route families remain the adopted candidate location for later explicitly frozen workbench slices, but the full target workbench is not active merely because bounded slices exist.

8B. Mockup-Observed Action/Event Sequence

Status:

- This section enumerates the action/event sequence directly visible in the mockup text.
- It is a workflow-intent summary, not a final API contract or implementation claim.
- The sequence should guide future UI planning, state-machine mapping, and proof selection, but each action still needs implementation-grade controls, data contracts, and failure behavior before coding.

Action/Event 1: user submits intent/specification

- Trigger: the user clicks the "Confirm/Submit Button".
- Input source: user natural-language query, manual/custom specification, or possibly both together.
- Current specificity boundary: the mockup explicitly leaves open whether natural-language and manual/custom inputs are exclusive, alternative, or combinable.
- Planning mapping: draft intent/source posture should move toward a committed session/selection-review boundary only after user confirmation.

Action/Event 2: retrieval/discovery locates candidate material

- Mockup text names RAG, vector embedding, semantic search, and other adequate/optimal/feasible methods.
- Candidate material may come from upstream feeders/storages/DBs, specified local directories/uploaded files, or other chooseable sources/directories/connectors/options.
- Output of this action ends up in Sublayer 3A / Gate B for material intake and session scoping.
- Current specificity boundary: repo-live proof currently supports token/query search over materialized APS retrieval chunks, not a confirmed Layer 3 RAG/vector/semantic implementation.

Action/Event 3: user reviews and admits or excludes loaded material

- The user confirms/approves the list of files/data/etc. loaded into Sublayer 3A / Gate B.
- The user may also deny, remove, isolate, or otherwise exclude material.
- Planning mapping: this is the user-facing Gate B review boundary.
- Current specificity boundary: deny/remove/isolate are mockup-observed actions, but their exact durable-state meanings are not finalized.

Action/Event 4: approved material is frozen and moved toward Gate C

- Approved retrieved material is loaded, initialized, stored, saved, or otherwise frozen in a temp/local/dedicated Layer 3 DB/storage.
- The mockup names this as a Post-3A / Pre-3B state.
- Each file or collection is verified/validated before being loaded/initialized into Sublayer 3B / Gate C.
- Planning mapping: this corresponds to session-scoped material snapshots and loading closure before typing/unit/group/set formation.
- Current specificity boundary: exact storage, retention, validation, immutability, and cleanup behavior remain unresolved.

Action/Event 5: user configures/orchestrates analysis execution

- After material is loaded into Sublayer 3B / Gate C, the user configures/specifies how analysis should be orchestrated, conducted, organized, or executed.
- This applies to qualitative, quantitative/deterministic, and hybrid/mixed analysis environments/containers/planes individually and together as a whole.
- The configuration must happen before files/data/content are fed into the analysis environments.
- The user authorizes/finalizes this configuration through another confirmation/authorization action.
- The mockup explicitly says this step is uniquely significant and not yet fully fleshed out.
- Planning mapping: this corresponds most closely to plan_review and analysis-plan approval.
- Current specificity boundary: exact orchestration fields, per-plane controls, defaults, validation rules, and rejection behavior are not yet defined.

Action/Event 6: analysis produces validated/finalized outputs

- Insights/facts/data are outputted, produced, or organized after the respective analysis environments execute, validate/verify, and finalize.
- Outputs are shown as specific to ingress objects.
- Planning mapping: this corresponds to reconciled_results and package_review surfaces, plus output provenance back to ingress objects, analysis units, sets, and pass runs.
- Current specificity boundary: output taxonomy, trace UI, package review behavior, and downstream handoff triggers are not finalized.

- upstream feeders/storages/DBs,

10. Sublayer 3A / Gate B: Material Intake And Session Scoping

Gate B is the first major durable Layer 3 boundary in the mockup.

Input to Gate B:

- retrieved data,
- files,
- connector results,
- upstream DB/storage records,
- local directory files,
- uploaded files,
- selected existing run artifacts,
- source collections.

Operator action at Gate B:

- User confirms/approves loaded files/data/content.
- User can deny/remove/isolate specific items.
- User can decide which materials should proceed into the session.

Backend requirement:

- Approved material should be saved/frozen to a temp/local/dedicated Layer 3 DB/storage.
- Each file or collection should be verified/validated.
- Each accepted item should have stable identity and provenance.
- Each accepted item should be traceable to the initial intent and source discovery path.

Repo-live mapping:

- L3Session maps to the durable session.
- L3SelectionManifest maps to the committed source/selection manifest.
- L3Descriptor maps to expanded selected source descriptors.
- L3RetrievalEvent maps to retrieval/load events and outcomes.
- L3MaterialSnapshot maps to saved/frozen material snapshots.
- layer3_session_entry.py owns commit_selection, expand_descriptors, record_retrieval_event, and finalize_session.

Important distinction:

- Repo-live backend has the core owner-service chain for this.
- Repo-live UI does not yet expose this as a full operator Gate B material review surface.

23. Proposed Workbench State Machine

Current repo-live planning docs already define a future broader workbench state machine. It maps well to the mockups:

1. draft_selection
   - User enters natural-language query and/or manual specification.
   - Editable.
   - No durable Layer 3 session yet.

2. selection_review
   - User reviews selected/retrieved candidate sources before commit.
   - Review plus commit only.
   - No silent mutation after commit.

3. loading
   - System retrieves/loads/validates/freeze material.
   - Read-only progress visibility.

4. typing_review
   - System shows typed units/groups/sets.
   - Operator can perform bounded override-only review.

5. plan_review
   - Operator reviews/approves/rejects bounded plan.
   - No execution side effects during review.

6. pass_monitor
   - Execution status, warnings, errors, and pass output visibility.
   - Rerun only where a later lane explicitly allows it.

7. reconciled_results
   - Read-only accepted versus quarantined output review.

8. package_review
   - Inspect package variants.
   - Bounded handoff initiation only if a later active lane explicitly admits it.

23A. State-To-Action And Data Contract

This is a planning contract, not a live API claim.

| State | Operator action | System action | Durable state expected | Must not happen |
| --- | --- | --- | --- | --- |
| draft_selection | Enter natural-language intent, manual/custom specification, or both | Validate draft shape only | Draft intent packet, not yet a Layer 3 session | No material persistence, no retrieval side effects unless explicitly preview-only |
| selection_review | Review candidate source selectors and submit/commit | Create session and selection manifest through owner service | L3Session and L3SelectionManifest | No silent mutation after commit |
| loading | Watch retrieval/materialization progress | Expand descriptors, record retrieval events, persist approved material snapshots, finalize loading closure | L3Descriptor, L3RetrievalEvent, L3MaterialSnapshot, session closure summary | No operator data edits, no browser-only state |
| typing_review | Inspect/override typing and grouping | Materialize typing records, units, groups, sets | L3TypingRecord, L3AnalysisUnit, L3AnalysisGroup, L3AnalysisSet | No unsupported typing silently admitted |
| plan_review | Approve/reject bounded analysis plan | Build plan but do not execute until approved | L3AnalysisPlan with auditable approval state | No execution side effects before approval |
| pass_monitor | Inspect execution status | Execute admitted pass runs and persist outputs/warnings/errors | L3PassRun and analysis artifacts/caveats | No hidden rerun/branch behavior |
| reconciled_results | Inspect accepted vs warning/quarantined results | Reconcile pass outputs and caveats | L3ReconciliationRecord candidate state | No loss of failed/excluded provenance |
| package_review | Inspect package variants and optionally initiate allowed handoff | Create package variants and, if admitted, handoff packages | L3OutputPackage and downstream handoff packages | No automatic broad handoff without explicit admission |
